# AUDIT SÉCURITÉ — Windows 11 Toolbox v3.2.0

> **Date** : 2026-10-30 · **Auditeur** : audit statique du code (aucune exécution, aucune modification de code)
> **Périmètre** : `Windows-Toolbox.ps1` (3202 lignes), `Updater-Toolbox.ps1`, `Installer-Toolbox.ps1`,
> `Uninstall-Toolbox.ps1`, `Build-Toolbox.ps1`, `Setup-GUI-Toolbox.ps1`, `Setup-Toolbox.cmd`,
> `Lancer-Toolbox.cmd`, `installer.iss`, `version.json`.
> **Exclusion** : le signalement Kaspersky PDM (faux positif documenté, voir en-tête du script
> `Windows-Toolbox.ps1:17-24`) n'est PAS compté comme finding.
> **Public cible** : techniciens de réparation PC (clients) — le niveau de menace inclut donc les
> machines des clients finaux, potentiellement contaminées par un malware utilisateur.

## 2. Réponses directes aux 7 questions de l'audit

1. **Chaîne d'auto-update** — Le SHA256 du manifeste **peut être contourné de deux façons** : (a) champ `sha256` retiré → vérification sautée silencieusement (F2, fail-open) ; (b) manifeste compromis → le hash fourni correspond au payload (F1 : le manifeste est juge et partie). `version.json` malformé est en revanche **bien géré** (fail-safe, F16). Le **downgrade est impossible** (comparaison strictement supérieure, F15). L'URL est **en HTTPS** avec TLS 1.2 forcé (F20) ; la protection de la branche `main` est une **recommandation forte** à mettre en œuvre (F1) — elle ne remplace pas la signature côté client.
2. **Injection de commandes** — **Confirmé : aucune entrée utilisateur n'est concaténée** dans les scripts exécutés par `Invoke-Expression` (F17). Les 2 seuls appels exécutent des chaînes en dur ; les 3 points d'entrée utilisateur (InputBox ×2, champ recherche, favoris) sont consommés comme données (nom de propriété exact, index entier, filtre d'affichage), jamais comme code.
3. **Registre** — Suppressions correctement scopées : l'app ne touche que ses propres valeurs (`HKCU\Software\WindowsToolbox`, valeur `WindowsToolbox` de la Run key), les corrections malwares exportent une sauvegarde `.reg` avant chaque suppression — mais la **sauvegarde n'est pas vérifiée** (F8) et le reset massif des policies manque de garde-fou domaine (F9).
4. **Secrets** — **Aucun secret en dur** (F19). Seule réserve mineure : le mot de passe PFX en ligne de commande du build (F14).
5. **Téléchargements** — TLS 1.2 forcé et HTTPS sur 100 % des canaux de l'app ; 2 HTTP résiduels hors canal critique (lien `hdtune.com`, timestamp DigiCert — F11).
6. **Élévation** — Justifiée et minimisée (F21) ; deux défauts : TOCTOU sur le fichier temporaire élevé (F4) et logique `GuiElevated`+args qui n'élève pas (F10).
7. **Sanitization des noms** — Conforme : noms générés depuis constantes + COMPUTERNAME + horodatage, aucun input utilisateur dans les chemins (F22).

## 3. Points forts relevés

- Vérification du SHA256 **en mémoire avant toute écriture disque** dans la GUI (`Windows-Toolbox.ps1:445-459`), puis validation de la syntaxe (`Parser::ParseFile`, 462-466) avant remplacement du fichier — l'ordre des contrôles est le bon.
- Détection d'anomalie d'intégrité au démarrage (`Test-ToolboxIntegrity`, 357-370) et sauvegarde `.bak`/`.reg` systématique côté updater CLI (`Updater-Toolbox.ps1:114`).
- Aucune télémétrie, aucune collecte, aucun endpoint non documenté : le seul trafic réseau est `raw.githubusercontent.com`, `github.com/releases` et les liens navigateurs affichés à l'utilisateur.
- Historique local limité et rotatif (`Windows-Toolbox.ps1:561-574`), désactivable/effaçable depuis l'UI (2780).
- Installateur Inno en `PrivilegesRequired=lowest` (`installer.iss:32`) : rien n'est écrit hors du profil utilisateur.

## 4. Verdict global

**SATISFAISANT AVEC CORRECTIFS PRIORITAIRES — publiable en open source après traitement de F1/F2/F3.**

Le code ne contient **ni secret, ni injection, ni exfiltration** ; les entrées utilisateur sont correctement cloisonnées ; l'élévation est rationnée et explicite ; TLS et HTTPS sont correctement appliqués. Le modèle de menace réel de l'outil se concentre sur **un seul point : la chaîne d'auto-update**, qui est aujourd'hui un mécanisme de RCE silencieux par procuration en cas de compromission du dépôt GitHub (compte volé, PR malveillante fusionnée) — le SHA256 transmis avec l'URL dans le même manifeste n'est pas une authentification, et son caractère optionnel (F2) l'affaiblit encore.

**Plan de correction priorisé :**
1. **F2** (fail-closed SHA256) — quelques lignes, gain immédiat, à faire en premier.
2. **F3** (whitelist des domaines d'URL de mise à jour) — défense en profondeur triviale.
3. **F1** (signature Authenticode vérifiée côté client + branche `main` protégée + publication par tags) — chantier principal ; l'infrastructure de signature existe déjà (`Build-Toolbox.ps1:40-56`), il ne manque que la vérification à la réception.
